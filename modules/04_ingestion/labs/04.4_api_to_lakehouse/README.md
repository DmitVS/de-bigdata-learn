## Objective

Загрузить в bronze два API: учебный `retail-api` маркетинговой системы (промо-акции по дням, с
ключом, пагинацией, лимитом частоты и сбоями) и публичный API праздников Nager.Date. Загрузка
должна переживать сбои API, грузить любую дату повторно без дублей, а данные — сходиться с
другими источниками сети или объяснимо расходиться с ними.

## Tasks

### Task 1. Разведка и контракт API

**Expected result / Definition of Done:**
- В README — контракт загрузки `retail-api`, полученный запросами (`curl`, Python), а не из
  кода сервера: формат ответа; где список записей; естественный ключ записи и вложенного товара;
  как устроена пагинация и как понять, что страницы кончились; какие коды ответа бывают и какие
  из них временные; сколько запросов в секунду проходит без 429
- Сколько страниц и записей за 2024-04-01 — посчитано проходом по всем страницам

**Steps:**
1. Коды и заголовки — урок 04, шаги 1–2 («Попробуй сам»).
2. Лимит частоты проверь сериями запросов разной плотности.

### Task 2. Загрузка промо

**Expected result / Definition of Done:**
- Скрипт грузит промо за диапазон дат в таблицу namespace `bronze` через dlt; в таблице **по
  строке на товар в акции** с датой, магазином и городом
- Загружена неделя 2024-04-01 … 2024-04-07; сверка с датасетом: для каждой даты число пар
  (магазин, товар) в bronze равно числу строк датасета с `activity_flag = 1` за эту дату —
  запрос в `queries.sql`
- Повторная загрузка 2024-04-03 не меняет число строк и суммы за эту дату (проверка в
  `queries.sql`); способ защиты от дублей описан в README
- Ключ API не встречается ни в коде, ни в git

**Steps:**
1. `RESTClient` с пагинатором — урок 04, шаг 5. Дата — параметр ресурса и поле каждой записи
   (урок 04, шаг 6).
2. Почему не оставить товары вложенным списком и не делать merge дочерней таблицы — урок 04,
   шаг 6, проверенная ловушка.
3. Прежде чем выбирать merge, оцени время: сколько строк за день и с какой скоростью идёт upsert
   в Iceberg (урок 01, шаг 5).

### Task 3. Устойчивость к сбоям

**Expected result / Definition of Done:**
- API перезапущен с 30% сбоев: `RETAIL_API_FAIL_RATE=0.3 make up PROFILES="ingestion"`
- Загрузка одной новой даты при 30% сбоев завершается успешно, данные сходятся с датасетом
  (тот же запрос сверки)
- В README — сколько запросов получили 503 и 429 за эту загрузку (по логам `make logs
  S=retail-api` или своим счётчикам) и почему загрузка всё равно полна
- После задачи API возвращён к обычной доле сбоев (`make up PROFILES="ingestion"` без
  переменной)

### Task 4. Праздники и флаг `holiday_flag`

**Expected result / Definition of Done:**
- Праздники КНР за 2024 год из Nager.Date загружены в bronze (декларативный `rest_api` или
  `RESTClient`)
- Запрос сравнивает праздники из API с днями, где в датасете `holiday_flag = 1`: какие дни флага
  объясняются выходными, какие — праздниками из API, какие не объясняются ничем, и есть ли
  выходные **без** флага
- В README — объяснение каждой группы расхождений: что на самом деле означает `holiday_flag` и
  чего не хватает в API (подсказка: официальный календарь КНР на 2024 год с переносами рабочих
  дней)

**Steps:**
1. День недели в DuckDB — `dayofweek(date)` (0 — воскресенье, 6 — суббота).
2. `dt` в датасете — строка; приведи типы обеих сторон к `DATE`.
