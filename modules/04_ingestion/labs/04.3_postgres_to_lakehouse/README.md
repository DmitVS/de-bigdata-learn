## Objective

Забрать справочники `retail_oltp` в bronze двумя способами — полной загрузкой и инкрементом по
`updated_at` — и выяснить измерением, что каждый способ теряет и сколько стоит. Починить
инкремент там, где это возможно, и принять решение для каждой таблицы.

## Tasks

### Task 1. Полная загрузка

**Expected result / Definition of Done:**
- Три таблицы `retail_oltp` загружены в namespace `bronze` целиком (replace); имена таблиц
  bronze показывают источник (договорись о правиле и запиши его в README)
- Время загрузки и число строк каждой таблицы записаны в README
- Сверка по трём уровням (урок 03, шаг 6) для каждой таблицы: расхождений 0 — запросы в
  `queries.sql`

**Steps:**
1. Источник — `sql_database` с `backend="pyarrow"` (урок 03, шаг 5).
2. Сверка в одном запросе DuckDB: `ATTACH` Postgres и Iceberg одновременно.

### Task 2. Инкремент и что он теряет

**Expected result / Definition of Done:**
- Второй вариант загрузки: те же таблицы инкрементально по `updated_at` с merge по ключу — в
  **другие** таблицы bronze (или другой namespace), чтобы сравнивать с полной загрузкой
- Сценарий: начальная загрузка → `retail_oltp_changes.py --changes 20 --seed 1` → загрузка
  обоими вариантами → сверка каждого варианта с источником
- В README — таблица: тип операции генератора → увидела ли полная загрузка → увидел ли
  инкремент. Число расхождений по каждой таблице
- Время начальной и повторной загрузки обоих вариантов

**Steps:**
1. Перед запуском запиши предсказание: какие операции инкремент пропустит (лаба 04.2, задача 3).
2. Первая инкрементальная загрузка — самая дорогая (урок 03, ловушка шага 5).

### Task 3. Починка инкремента

**Expected result / Definition of Done:**
- В `retail_oltp` добавлен триггер, выставляющий `updated_at` при UPDATE, на всех трёх таблицах
  (файл `capstone/oltp/triggers.sql`)
- В инкрементальной загрузке включено окно перечитывания; его размер обоснован в README
- Повтор сценария из задачи 2 (с новым `--seed`) и сценария долгой транзакции (`--slow-tx`,
  загрузка во время транзакции и после): какие потери закрыты, какие остались — сверкой
- В README — чем закрыть оставшиеся потери (урок 01, шаги 3–4)

**Steps:**
1. Триггер — урок 03, шаг 4. Одну функцию можно повесить на три таблицы.
2. Окно перечитывания — `lag` у `dlt.sources.incremental` (урок 02, шаг 5).
3. Чтобы поймать долгую транзакцию, загрузка должна пройти, пока она открыта, а ещё одно
   изменение — зафиксироваться после её начала (урок 01, шаг 3).

### Task 4. Решение

**Expected result / Definition of Done:**
- В README — ADR (модуль 01, урок 06): для каждой из трёх таблиц способ загрузки (полная или
  инкремент), способ записи и как ловятся удаления; аргументы — твои замеры времени и
  найденные потери, а не общие слова
- `capstone/ingestion/load_oltp.py` после решения грузит выбранным способом; повторный запуск
  без изменений в источнике не меняет данные bronze (сверка)
