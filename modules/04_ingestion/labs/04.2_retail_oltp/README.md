## Objective

Поднять «учётную систему» сети — справочники магазинов, товаров и ассортимента в Postgres
`retail_oltp`, выведенные из FreshRetailNet, — и научиться видеть, что в ней меняется. Эта база —
источник для лабы 04.3, snapshots в модуле 05 и CDC в модуле 08.

## Контракт схемы

Генератор изменений работает именно с этими таблицами и колонками. Имена и типы менять нельзя,
ограничения выбираешь ты.

| Таблица | Колонки | Ключ |
|---|---|---|
| `stores` | `store_id bigint`, `city_id bigint`, `status text` (`open` / `closed`), `opened_on date`, `updated_at timestamptz` | `store_id` |
| `products` | `product_id bigint`, `management_group_id bigint`, `first_category_id bigint`, `second_category_id bigint`, `third_category_id bigint`, `is_active boolean`, `updated_at timestamptz` | `product_id` |
| `assortment` | `store_id bigint` → `stores`, `product_id bigint` → `products`, `listed_on date`, `updated_at timestamptz` | `(store_id, product_id)` |

## Tasks

### Task 1. Схема

**Expected result / Definition of Done:**
- `capstone/oltp/schema.sql` создаёт три таблицы по контракту с первичными и внешними ключами,
  `NOT NULL` там, где значение обязательно, `CHECK` на `status`, значения по умолчанию и индекс
  для будущего курсора
- Применяется командой `psql … -f capstone/oltp/schema.sql` к пустой базе без ошибок; команда
  записана в README
- Триггеров **пока нет**: они появятся в лабе 04.3

**Steps:**
1. Синтаксис — урок 03, шаг 1. Подключение из `make shell`: переменные `PGHOST`, `PGUSER`,
   `PGPASSWORD` из окружения (урок 01, «Попробуй сам» шага 3).
2. Подумай, какое значение по умолчанию у `updated_at` и почему оно не поможет при UPDATE.

### Task 2. Наполнение из датасета

**Expected result / Definition of Done:**
- Скрипт наполнения выводит справочники из `data/raw/…/*.parquet` и пишет в `retail_oltp`:
  898 магазинов, все товары датасета, все пары магазин × товар
- Перед наполнением проверено, что `any_value` (или другое правило) корректно: у магазина один
  город, у товара одна категория каждого уровня и одна `management_group_id`. Запросы — в
  `queries.sql`
- `opened_on` и `listed_on` — первая дата, когда магазин или пара встречаются в данных;
  `updated_at` — фиксированный момент начальной загрузки (одно значение на все строки)
- Повторный запуск наполнения на заполненной базе не создаёт дублей и не падает (или падает с
  понятной ошибкой — опиши, что выбрал и почему)

**Steps:**
1. DuckDB с расширением `postgres` — урок 03, шаг 2.
2. Порядок записи таблиц задают внешние ключи.

### Task 3. Изменения и их следы

**Expected result / Definition of Done:**
- Зафиксирован момент `T0` (`SELECT now()`), затем выполнен `python
  scripts/retail_oltp_changes.py --changes 20 --seed 1`
- Запросами к `retail_oltp` (и к датасету для сравнения) найдены **все** 20 изменений по типам:
  сколько строк с `updated_at > T0` в каждой таблице; какие товары сменили категорию; какие
  пары ассортимента пропали и появились; какой магазин новый
- В README — таблица «тип операции → видна ли по `updated_at` → как её найти иначе»

**Steps:**
1. Вывод генератора подскажет, что искать, но найти нужно запросами, а не по выводу.
2. Пропавшие строки по `updated_at` не найти — сравни с тем, что было (урок 03, шаг 6:
   `ANTI JOIN`).

### Task 4. Долгая транзакция

**Expected result / Definition of Done:**
- Во время `python scripts/retail_oltp_changes.py --slow-tx 30` запрос к `pg_stat_activity`
  показывает открытую транзакцию: её `xact_start`, состояние, запрос
- Из второй сессии во время транзакции изменённая строка видна со **старым** значением, после
  фиксации — с новым; запросы и результаты в `queries.sql`
- В README — объяснение, почему `updated_at` этой строки меньше времени, когда она стала видна, и
  чем это опасно для инкремента
