## Objective

Получить в каталоге граф capstone от источника через Spark и dbt до дашборда — по таблицам и по
колонкам — и использовать его для двух рабочих задач: анализа влияния изменения и поиска причины
инцидента.

## Tasks

### Task 1. Граф без Spark

**Expected result / Definition of Done:**
- В README — граф витрины capstone в каталоге после сбора dbt и Superset: где он начинается и
  почему именно там
- Анализ влияния тем же вопросом двумя способами: `dbt ls -s <модель>+` и вкладка Lineage в
  каталоге; в чём разница результатов

### Task 2. Spark через OpenLineage

**Expected result / Definition of Done:**
- Задача Spark capstone запускается с агентом OpenLineage; события пишутся в каталог и в файл
- В каталоге у таблицы, которую пишет Spark, есть предок-пайплайн из сервиса `openlineage`;
  граф идёт от таблицы-источника Spark до дашборда без разрывов
- В README — разбор одного события `COMPLETE` из файла: задача, входы, выходы, `symlinks`,
  `columnLineage` для двух колонок
- Если какое-то ребро не появилось — причина из лога сервера OpenMetadata и решение

**Steps:**
1. Создай пайплайн задачи в сервисе `openlineage` заранее (имя — `<namespace>-<имя приложения>`;
   образец — `demo/om_demo_setup.py`) и запусти задачу: `make spark-lineage JOB=capstone/…py`.
2. Найди в логе сервера строки `OpenLineageMapper` / `OpenLineageEntityResolver`.
3. Если вход — файлы, подумай, как сделать его таблицей (образец — `demo/spark_store_sales.py`).

### Task 3. Две задачи на графе

**Expected result / Definition of Done:**
- Анализ влияния: «переименовываем колонку `<…>` в bronze» — список затронутых колонок, витрин и
  дашбордов по lineage колонок; что из этого покажет и что не покажет `dbt ls`
- Поиск причины: воспроизведи инцидент (например, обнули часы без товара за один день в bronze)
  и пройди по графу от дашборда вверх до места ошибки; шаги и что ты видел на каждом — в README
- Владельцы затронутых таблиц определены по каталогу (лаба 11.1)
