# 02 · pre-commit: проверки до коммита

> [!info] Урок одной фразой
> Линтеры у нас есть (`make lint`), но их надо помнить запускать. pre-commit — охранник у двери
> git. Перед каждым коммитом он сам проверяет изменённые файлы и часть ошибок чинит на месте.
> Коммит с секретом или сломанным YAML он просто не пускает. Ошибка, пойманная за секунду до коммита,
> стоит дешевле всего: её ещё не видел ни CI, ни коллега.

> [!todo] Чек-лист: после урока ты сможешь
> - [ ] объяснить, что такое git-хук и чем фреймворк pre-commit удобнее самописного хука;
> - [ ] прочитать и дополнить `.pre-commit-config.yaml`: репозитории хуков, локальные хуки, исключения;
> - [ ] запустить проверки в контейнере: по изменённым файлам и по всем;
> - [ ] объяснить, почему хуки берут линтеры из `uv.lock`, а не свои копии;
> - [ ] разобрать отказ pre-commit и починить причину, а не обойти её.

## Шаг 1. Git-хуки и зачем фреймворк

**Проблема.** `make lint` ловит ошибки, но его забывают запустить. Ошибку стиля находит CI через
пять минут, секрет в `.env` — уже никто: он в истории git навсегда.

**Как устроено.** Git умеет вызывать скрипты на событиях: перед коммитом (`pre-commit`), перед
отправкой (`pre-push`) и т.д. Это **хуки** — файлы в `.git/hooks/`. Если хук вернул ненулевой код,
коммит отменяется. Писать хуки руками неудобно: нужно выбрать изменённые файлы, разные проверки
для разных типов, поставить хук каждому участнику.

Фреймворк **pre-commit** решает это одним файлом `.pre-commit-config.yaml` в корне репозитория:

1. Ты перечисляешь проверки (хуки) и к каким файлам они относятся.
2. `pre-commit run` берёт файлы из индекса git (то, что ты добавил `git add`), раздаёт каждому
   хуку его файлы и собирает результат.
3. Хуки бывают проверяющие (`check-yaml`) и чинящие (`end-of-file-fixer`, `ruff format`). Если
   хук что-то исправил, он тоже возвращает ошибку: проверь правку, сделай `git add` и коммить снова.

**Что из этого следует.** Одни и те же правила работают у всех участников и в CI. Конфиг лежит в
git, его ревьюят, как код.

## Шаг 2. Наш конфиг

**Проблема.** pre-commit по умолчанию ставит каждому хуку своё окружение и свою версию линтера.
Тогда ruff в хуке и ruff в `make lint` и CI могут быть разных версий и спорить друг с другом.

**Как устроено.** Файл `.pre-commit-config.yaml` в корне курса:

```yaml
exclude: ^(data/|.*/dbt_packages/|.*/target/|.*/edr_target/|.*/node_modules/|.*/\.evidence/)  # ①

repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks       # ② готовые хуки
    rev: v6.0.0
    hooks:
      - id: check-yaml
        args: [--unsafe]                                         #   теги !reset в compose
      - id: detect-private-key
      - id: end-of-file-fixer
        exclude: (\.canvas$|^\.obsidian/)                        # ③
  - repo: local                                                  # ④ свои хуки
    hooks:
      - id: ruff-check
        entry: ruff check --fix
        language: system                                         # ⑤ ruff из venv образа
        types: [python]
      - id: no-env-file
        entry: .env попал в коммит — секреты храни только локально
        language: fail                                           # ⑥ всегда падает
        files: (^|/)\.env$
```

| Метка | Что важно |
|---|---|
| ① | общий список исключений: данные, скачанные пакеты, сборки |
| ② | хуки из внешнего репозитория; `rev` — версия; при первом запуске pre-commit их скачивает в кэш |
| ③ | Obsidian сохраняет карты без перевода строки в конце; без исключения хук правил бы их после каждого сохранения |
| ④ | `repo: local` — хуки, описанные прямо здесь |
| ⑤ | `language: system` — команда из окружения, где запущен pre-commit; у нас это venv образа workspace с версиями из `uv.lock` — те же, что в `make lint` и CI |
| ⑥ | `language: fail` — хук-запрет: падает, если ему достались файлы; так `.env` не попадёт в коммит |

**Что из этого следует.** Правило «одна версия линтера везде» держится на `language: system`:
pre-commit, `make lint` и CI запускают одни и те же ruff, sqlfmt и yamllint.

> [!warning] Ловушка
> Не добавляй в конфиг хуки ruff из их репозитория (`astral-sh/ruff-pre-commit`), если ruff уже
> в `uv.lock`. Появятся две версии линтера, и они начнут спорить о форматировании.

## Шаг 3. Как это запускается у нас

**Проблема.** pre-commit — Python-пакет. По нашему правилу на хосте ставить его нельзя. А git
вызывает хук на хосте.

**Как устроено.** Две части:

- **pre-commit живёт в образе workspace** (группа `dev`). Команда `make precommit` запускает его
  в контейнере; `make precommit ARGS="--all-files"` — по всем файлам.
- **Хук git — короткий скрипт** `scripts/git-hooks/pre-commit`: он вызывает `make precommit`.
  `make hooks` копирует его в `.git/hooks/`. На хосте по-прежнему нужны только docker и make.

```mermaid
sequenceDiagram
    autonumber
    participant U as git commit (хост)
    participant H as .git/hooks/pre-commit
    participant M as make precommit
    participant W as workspace: pre-commit
    U->>H: перед коммитом
    H->>M: make -s precommit
    M->>W: docker compose exec workspace pre-commit run
    W->>W: файлы из индекса → хуки
    W-->>U: код 0 — коммит; не 0 — отказ и список ошибок
```

Хук и кэш работают, когда корень курса — сам git-репозиторий (решение о выносе курса в
отдельный репозиторий, лаба 12.1). Кэш скачанных хуков — `data/.pre-commit`.

**Что из этого следует.** Первый запуск скачивает хуки из GitHub — это занимает десятки секунд.
Дальше полный прогон по всем файлам курса — около 17 с.

> [!example]- Попробуй сам: прогон по всем файлам
> Нужен корень курса с `.git` (после выноса в отдельный репозиторий, лаба 12.1).
> ```bash
> make precommit ARGS="--all-files"
> ```
> **Увидишь:** строки вида `check yaml……Passed`, `ruff check……Passed`, `sqlfmt……Passed`,
> `.env не коммитим……(no files to check)Skipped`. На копии курса от 2026-10-03 хук
> `trailing-whitespace` исправил два файла с пробелами в конце строк. Хук `end-of-file-fixer`
> поймал сгенерированный файл Elementary, поэтому `edr_target/` добавлен в исключения.
> **Почему:** с `--all-files` хуки получают все файлы репозитория, а не только индекс. Хук,
> который исправил файл, тоже возвращает `Failed`: правку надо посмотреть и добавить в коммит.

## Шаг 4. Когда pre-commit говорит «нет»

**Проблема.** Хук отказал, а коммит срочный. Соблазн — `git commit --no-verify`.

**Как устроено.** Типовые отказы и что они значат:

| Сообщение | Что случилось | Что делать |
|---|---|---|
| `Failed … files were modified by this hook` | хук исправил файл | посмотреть `git diff`, `git add`, коммит |
| `Your pre-commit configuration is unstaged` | конфиг изменён, но не в индексе | `git add .pre-commit-config.yaml` |
| `.env попал в коммит — секреты храни только локально` | в индексе `.env` | `git rm --cached .env`; проверить `.gitignore` |
| `detect private key … Failed` | в файле похоже на приватный ключ | убрать ключ, ключ считать скомпрометированным |
| ошибка ruff / sqlfmt / yamllint | нарушение стиля | исправить; `make fmt` чинит формат |

**Что из этого следует.** `--no-verify` пропускает проверки, но не отменяет их: тот же lint
запустит CI. Обход хука переносит ошибку на пять минут позже и на чужие глаза.

## Сборка целиком

| Слой проверок | Когда | Сколько ждать | Что ловит |
|---|---|---|---|
| pre-commit | перед каждым коммитом | секунды | стиль, формат, YAML/JSON, секреты, большие файлы |
| CI (урок 03) | на pull request | минуты | то же + тесты + сборка dbt без нашего стека |
| Тесты данных (модуль 09) | при каждом запуске пайплайна | минуты | ошибки в данных |

## Шпаргалка

| Хочу | Как |
|---|---|
| Проверить изменённые файлы | `make precommit` |
| Проверить всё | `make precommit ARGS="--all-files"` |
| Один хук | `make precommit ARGS="ruff-check --all-files"` |
| Поставить хук git | `make hooks` (нужен `.git` в корне курса) |
| Обновить версии внешних хуков | `pre-commit autoupdate` в `make shell` |
| Пропустить хук один раз | `SKIP=sqlfmt git commit …` — только осознанно |

## Типичные ошибки

| Симптом | Причина | Как проверить | Как чинить |
|---|---|---|---|
| Хук правит один и тот же файл после каждого сохранения | программа (Obsidian) пишет файл по-своему | какие файлы в `Fixing` | исключить их из этого хука |
| В хуке и в CI разный результат ruff | две версии линтера | `rev` хуков ruff | `language: system`, одна версия из `uv.lock` |
| `make hooks`: нет `.git` | курс ещё внутри общего репозитория | `ls -a` | вынести курс в свой репозиторий (лаба 12.1) |

## Проверь себя

Карточки — в [flashcards.md](../flashcards.md).

> [!question] 1. Хук `ruff format` исправил файл и вернул `Failed`. Почему он не пропустил коммит, раз всё починил?
> > [!success]- Ответ
> > Исправления не в индексе: коммит содержал бы старую версию файла. Нужно посмотреть правку и
> > добавить её `git add`.

> [!question] 2. Зачем хук-запрет на `.env`, если `.env` есть в `.gitignore`?
> > [!success]- Ответ
> > `.gitignore` не защищает от `git add -f` и от ошибки в самом `.gitignore`. Хук — вторая линия.

> [!question] 3. Почему наши хуки ruff и sqlfmt — `language: system`, а не репозитории хуков?
> > [!success]- Ответ
> > Чтобы версии совпадали с `uv.lock`, `make lint` и CI. Иначе разные версии будут спорить о
> > форматировании.
