# 04 · Документация и lineage в dbt: описания, сайт, граф и анализ влияния

> [!info] Урок одной фразой
> Технологическая карта блюда — описание рецепта и каждого ингредиента — хранится рядом с самим
> рецептом, поэтому не устаревает. Из всех карт кухня собирает меню-справочник с картой
> происхождения: откуда пришёл каждый ингредиент и в какие блюда он идёт. По этой карте видно,
> какие блюда снять с подачи, если поставщик привёз испорченную рыбу.

> [!todo] Чек-лист: после урока ты сможешь
> - [ ] описать модели и колонки в YAML и вынести длинный текст в docs-блок;
> - [ ] сохранить описания в базу как комментарии (`persist_docs`);
> - [ ] собрать и открыть сайт `dbt docs` и найти на нём граф;
> - [ ] выбрать предков и потомков модели селекторами и ответить «что затронет изменение»;
> - [ ] прочитать `manifest.json` скриптом и найти узлы без описания;
> - [ ] описать внешнего потребителя (exposure) и включить его в граф (лаба 05.4).

## Шаг 0. Азбука: технологические карты и карта происхождения

| В dbt | В аналогии «кухня» | Подробнее |
|---|---|---|
| `description` в YAML | Технологическая карта рецепта | [документация как код](../../../glossary/docs-as-code.md) |
| docs-блок | Длинная карта на отдельном листе, на которую ссылаются | [документация как код](../../../glossary/docs-as-code.md) |
| `persist_docs` | Наклейка с описанием прямо на контейнере | [документация как код](../../../glossary/docs-as-code.md) |
| Сайт `dbt docs` | Меню-справочник ресторана | [документация как код](../../../glossary/docs-as-code.md) |
| Lineage (происхождение) | Карта: какой ингредиент в какие блюда идёт | [lineage](../../../glossary/lineage.md) |
| Exposure | Внешний клиент: банкетный зал, куда уходят блюда | [lineage](../../../glossary/lineage.md) |
| `manifest.json` | Полная опись кухни в машинном виде | [граф dbt](../../../glossary/dbt-dag.md) |

## Шаг 1. Описания рядом с кодом

**Проблема.** Документация в вики устаревает через месяц: модель поменяли, а страницу — нет.
Аналитик видит колонку `oos_share` и не знает, это доля часов или доля дней.

**Как устроено.** В dbt описания живут **в тех же YAML-файлах**, что и тесты, рядом с
моделями. Изменение модели и её описания — один коммит, одно ревью.

```yaml
models:
  - name: stg_weather
    description: "Погода магазина за день: одна строка на магазин и дату"   # ① модель
    columns:
      - name: store_id
        description: "Магазин (ID датасета)"                                 # ② колонка
      - name: precipitation
        description: "{{ doc('precipitation') }}"                            # ③ docs-блок
```

**Docs-блок** — именованный кусок markdown в любом `.md` внутри `models/`. Нужен для длинных
текстов и для описаний, которые повторяются в нескольких моделях: написал один раз — сослался
везде.

```markdown
{% docs precipitation %}
Осадки за день из датасета (`precpt`). Единицы в описании датасета не указаны; используем
только для сравнения дней между собой.
{% enddocs %}
```

**Что писать в описании.** Не пересказ имени колонки («store_id — ID магазина» почти бесполезно),
а то, чего из имени не понять: **grain** модели (модуль 00, урок 09), единицы и формула,
источник, ограничения и подвохи. У витрин — на какой бизнес-вопрос она отвечает.

## Шаг 2. `persist_docs`: описания в базе

**Проблема.** Аналитик открывает витрину не на сайте dbt, а в DBeaver или Superset. Описаний там
нет.

**Как устроено.** Настройка `persist_docs` просит dbt после построения записать описания в базу
как **комментарии** (`COMMENT ON TABLE … IS …`, `COMMENT ON COLUMN …`). Любой клиент базы их
увидит: в DuckDB — в `duckdb_tables().comment` и `duckdb_columns().comment`.

```yaml
# dbt_project.yml
models:
  weather_demo:
    +persist_docs: {relation: true, columns: true}
```

> [!warning] Ловушка: публикация в Iceberg не переносит комментарии
> Наш хук публикации (урок 02) делает `CREATE TABLE … AS SELECT` в Iceberg — комментарии DuckDB
> туда не копируются. Описания для потребителей Iceberg приходят из каталога данных (модуль 11),
> который читает их из `manifest.json` dbt.

## Шаг 3. Сайт `dbt docs`

**Проблема.** Описания в YAML удобно писать, но неудобно читать. Нужен справочник, по которому
можно кликать: модель → колонки → откуда она → куда идёт.

**Как устроено.** Две команды:

1. `dbt docs generate` собирает два файла в `target/`: `manifest.json` (все узлы проекта, их SQL,
   описания, зависимости) и `catalog.json` (что реально лежит в базе: колонки, типы,
   статистика). Для второго dbt подключается к базе.
2. `dbt docs serve` поднимает маленький веб-сервер, который отдаёт `index.html` и эти два
   файла. Сайт статический: его можно положить на любой хостинг (в модуле 12 — на GitHub Pages
   из CI).

На сайте у каждой модели — описание, колонки с типами и описаниями, SQL (исходный и
скомпилированный), тесты, а в правом нижнем углу кнопка графа (**lineage graph**) с предками и
потомками.

> [!example]- Попробуй сам: сайт документации демо-проекта
> В `make shell`, папка `modules/05_transformation_dbt/demo`:
> ```bash
> dbt docs generate
> dbt docs serve --host 0.0.0.0 --port 8580 --no-browser     # остановить — Ctrl+C
> ```
> Открой в браузере на хосте `http://localhost:8580`. Найди `mart_city_rainy_days`, открой
> описание (текст из docs-блока), колонки, вкладку `Code`, затем граф (значок внизу справа).
> Отдельно, в другом окне `make shell`:
> ```bash
> duckdb -readonly /workspace/data/demo_weather.duckdb -c "select table_name, comment from duckdb_tables() where comment is not null"
> ```
> **Увидишь:** на сайте граф `raw.train`, `raw.eval` → `stg_weather` → `int_city_weather_daily` →
> две витрины → exposure `weather_report`. В DuckDB — описания двух таблиц marts.
> **Почему:** сайт собран из `manifest.json` и `catalog.json`; комментарии записал `persist_docs`.
> Порт 8580 опубликован у workspace специально для этого.

## Шаг 4. Lineage и анализ влияния через селекторы

**Проблема.** Источник собирается поменять колонку. Что сломается? Или наоборот: витрина
показывает странные цифры. Откуда они пришли?

**Как устроено.** **Lineage** (происхождение данных) — граф «что из чего получено». В dbt он
строится из `ref`/`source` **статически**, по коду, ещё до запуска. Подробная теория lineage —
модуль 11. Здесь — два практических вопроса:

| Вопрос | Направление | Селектор |
|---|---|---|
| **Анализ влияния** (impact analysis): что затронет изменение X? | вниз, к потомкам | `dbt ls -s X+` |
| **Поиск причины** (root cause): откуда пришли данные Y? | вверх, к предкам | `dbt ls -s +Y` |

Синтаксис селекторов:

| Запись | Что выбирает |
|---|---|
| `m+` / `+m` | модель и всех потомков / всех предков |
| `m+1`, `2+m` | на 1 уровень вниз / на 2 уровня вверх |
| `@m` | модель, потомков и **всех предков потомков** — всё, что нужно, чтобы пересобрать потомков |
| `path:models/marts`, `marts` | по папке |
| `tag:daily`, `source:raw+` | по тегу; всё, что зависит от источника |
| `exposure:weather_report` | внешний потребитель (шаг 5) |
| `a b` / `a,b` | объединение / пересечение |
| `state:modified+` | изменённое относительно сохранённого `manifest.json` и потомки (CI, модуль 12) |

> [!example]- Попробуй сам: что затронет изменение staging и что изменилось в коде
> В `make shell`, папка `modules/05_transformation_dbt/demo`:
> ```bash
> dbt ls -s stg_weather+ --quiet                                   # всё ниже по графу
> dbt ls -s +exposure:weather_report --quiet --resource-type model # что нужно отчёту
> dbt parse --quiet && mkdir -p /tmp/prod_state && cp target/manifest.json /tmp/prod_state/
> sed -i 's/round(avg(avg_temperature), 2)/round(avg(avg_temperature), 1)/' models/marts/mart_city_rainy_days.sql
> dbt ls -s state:modified+ --state /tmp/prod_state --quiet        # что изменилось и его потомки
> sed -i 's/round(avg(avg_temperature), 1)/round(avg(avg_temperature), 2)/' models/marts/mart_city_rainy_days.sql
> ```
> **Увидишь:** у `stg_weather+` — `int_city_weather_daily`, обе витрины, все их тесты (включая
> unit-тест) и `exposure:weather_demo.weather_report`. Отчёту нужны три модели цепочки. После
> правки `state:modified+` даёт `mart_city_rainy_days`, её тесты и exposure.
> **Почему:** селектор идёт по рёбрам графа в нужную сторону; `state:modified` сравнивает
> контрольные суммы узлов с сохранённым manifest. Это основа «slim CI» в модуле 12: строить и
> тестировать только изменённое.

> [!warning] Ловушка: lineage dbt знает только про dbt
> Граф начинается с `source()` и кончается моделями или exposures. Что делает загрузчик до
> bronze (модуль 04) и кто читает Iceberg после публикации, dbt не знает, если ты не описал
> exposure. Сквозной lineage от источника до дашборда — модуль 11 (OpenLineage, OpenMetadata).

## Шаг 5. Exposures: внешние потребители в графе

**Проблема.** Витрину читает дашборд. Если её сломать, пострадает дашборд, но в графе dbt его
нет.

**Как устроено.** **Exposure** — описание внешнего потребителя в YAML: тип (`dashboard`,
`notebook`, `analysis`, `ml`, `application`), владелец, зрелость и **от каких моделей он
зависит**. dbt ничего с ним не строит, но показывает в графе и выбирает селекторами.

```yaml
exposures:
  - name: weather_report
    label: "Отчёт «Погода и продажи по городам»"
    type: dashboard
    maturity: low
    depends_on:
      - ref('mart_city_rainy_days')
    owner:
      name: Команда данных курса
```

**Что из этого следует.** «Можно ли удалить колонку?» — `dbt ls -s модель+` покажет, есть ли
потребители. Без exposures ответ «никто» может оказаться неправдой.

## Шаг 6. `manifest.json`: граф для своих скриптов

**Проблема.** Нужна проверка «у каждой модели marts есть описание, иначе CI падает». Или отчёт
«модели без тестов». Сайт для этого не годится — нужен машинный доступ к графу.

**Как устроено.** `dbt parse` (и любая команда) пишет `target/manifest.json`. В нём:

| Ключ | Что |
|---|---|
| `nodes` | модели, тесты, seeds, snapshots: `name`, `resource_type`, `description`, `columns`, `config`, `depends_on.nodes`, `original_file_path`, `fqn` |
| `sources`, `exposures` | источники и потребители |
| `parent_map`, `child_map` | граф: `id → [родители]` / `id → [дети]` |

Идентификатор узла — `model.<проект>.<модель>`, `source.<проект>.<группа>.<таблица>`.

```python
import json
manifest = json.load(open("target/manifest.json"))
node = manifest["nodes"]["model.weather_demo.mart_city_rainy_days"]
print(node["description"][:40], node["depends_on"]["nodes"])
print(manifest["child_map"]["model.weather_demo.stg_weather"])
```

Есть и путь без Python: `dbt ls -s marts --resource-type model --output json --output-keys
"name description"` печатает по JSON-строке на модель.

> [!example]- Попробуй сам: описания моделей marts одной командой
> В `make shell`, папка `modules/05_transformation_dbt/demo`:
> ```bash
> dbt ls -s marts --resource-type model --quiet --output json --output-keys "name description" \
>   | python -c "import json,sys; [print(r['name'], '→', (r['description'] or '—')[:50]) for r in map(json.loads, sys.stdin)]"
> ```
> **Увидишь:** `fct_city_weather_daily → Погода города за день; …` и `mart_city_rainy_days →
> Сколько дождливых дней …`.
> **Почему:** `dbt ls` выводит по JSON-объекту на строку; без разбора в Python кириллица
> напечаталась бы escape-последовательностями `П…`.

**Что из этого следует.** Проверки «у всех есть описание», «у всех marts есть тест ключа»,
«нет `source()` вне staging» пишутся как короткий скрипт по manifest с ненулевым кодом выхода
при нарушении. Такой скрипт ты напишешь в лабе 05.4, а в модуле 12 он встанет в CI.

## Сборка целиком

Как ответить на вопрос «источник переименует колонку `precpt` — что сломается?»:

```mermaid
sequenceDiagram
    autonumber
    participant Q as Вопрос
    participant L as dbt ls
    participant M as manifest.json
    participant D as Сайт docs
    Q->>L: dbt ls -s source:raw+
    L->>M: обход child_map от источника
    M-->>L: stg_weather → int → 2 витрины → exposure
    L-->>Q: список моделей, тестов, потребителей
    Q->>D: открыть stg_weather: где используется precpt
    D-->>Q: колонка precipitation, docs-блок, SQL
    Q->>Q: правка в одном месте — stg_weather; потребители — из exposures
```

| Шаг | Если пропустить | Последствие |
|---|---|---|
| exposures не описаны | список потребителей неполон | «никто не читает» — а дашборд сломался |
| описания пустые | непонятно, что значит колонка | неверное использование витрины |
| нет `source()` | граф начинается с моделей | влияние изменения источника не видно |

## Шпаргалка

| Хочу | Как |
|---|---|
| Описать модель / колонку | `description:` в YAML рядом с тестами |
| Длинный общий текст | `{% docs имя %}…{% enddocs %}` в `.md` + `"{{ doc('имя') }}"` |
| Описания в базе | `+persist_docs: {relation: true, columns: true}` |
| Сайт документации | `dbt docs generate` → `dbt docs serve --host 0.0.0.0 --port 8580 --no-browser` |
| Что затронет изменение | `dbt ls -s модель+` |
| Откуда данные | `dbt ls -s +модель` |
| Изменённое против prod | `dbt ls -s state:modified+ --state <папка с manifest>` |
| Внешний потребитель | `exposures:` с `depends_on: [ref(…)]` |
| Граф в скрипте | `target/manifest.json`: `nodes`, `parent_map`, `child_map` |
| Список моделей в JSON | `dbt ls --output json --output-keys "name description"` |

## Типичные ошибки

| Симптом | Причина | Как проверить | Как чинить |
|---|---|---|---|
| На сайте нет колонок и типов | не выполнен `docs generate` после сборки или нет подключения | есть ли `target/catalog.json` | `dbt docs generate` после `dbt build` |
| `dbt docs serve` не открывается с хоста | слушает только `localhost` контейнера или другой порт | флаги команды | `--host 0.0.0.0 --port 8580` |
| Описание колонки не появилось | имя колонки в YAML не совпадает с SQL | `dbt docs generate` предупреждает? сравни имена | исправить имя |
| `doc('…') not found` | имя docs-блока с опечаткой или файл вне `models/` | путь `.md` | поправить имя / положить в `models/` |
| `state:modified` выбирает всё | `--state` указывает на manifest другой версии dbt или пустую папку | содержимое папки state | сохранить manifest нужной сборки |

## Проверь себя

Карточки — в [flashcards.md](../flashcards.md).

> [!question] 1. Почему описание в YAML рядом с моделью надёжнее страницы в вики?
> > [!success]- Ответ
> > Изменение модели и описания проходит в одном коммите и ревью. Описание видно там, где правят
> > код, и попадает на сайт и в базу автоматически. Вики живёт отдельно и устаревает.

> [!question] 2. Чем `dbt ls -s m+` отличается от `dbt ls -s @m`?
> > [!success]- Ответ
> > `m+` — модель и потомки. `@m` — ещё и все предки этих потомков: всё, что понадобится, чтобы
> > собрать потомков с нуля в пустой базе (например, в CI).

> [!question] 3. Ты собираешься удалить колонку из `mart_city_rainy_days`. Какие две проверки сделаешь?
> > [!success]- Ответ
> > `dbt ls -s mart_city_rainy_days+` — какие модели, тесты и exposures зависят от витрины; и
> > поиск колонки в коде потомков (на сайте docs или `grep` по `models/`). Exposure покажет
> > дашборд, которому колонка может быть нужна.

> [!question] 4. Где описание колонки увидит пользователь Trino, читающий опубликованную в Iceberg витрину?
> > [!success]- Ответ
> > Не увидит: публикация делает CTAS без комментариев. Описания придут из каталога данных
> > (модуль 11), который читает `manifest.json`, или придётся переносить их отдельно.
