# Лаба 09.3 · SLO pipeline и разбор инцидента по lineage

**Модуль:** [09 · Качество и наблюдаемость](../../README.md) · **Дата начала:** YYYY-MM-DD · **Статус:** ⬜

## Objective

Сформулировать, что сеть может обещать пользователям витрин (свежесть, успешность), измерить это
по истории и пережить настоящий инцидент: намеренно сломать источник, найти место по lineage,
восстановить данные и написать постмортем без поиска виноватых.

## Tasks

### Task 1. SLO

**Expected result / Definition of Done:**
- В [`ops/slo.md`](../../../../ops/slo.md) — минимум три SLO capstone: свежесть витрины, успешность
  ночного запуска, сверка bronze с источником; у каждого SLI — запрос или источник данных, цель
  через перцентиль или долю, бюджет ошибок, кто узнаёт о нарушении
- Значения SLI посчитаны по истории (запуски Dagster, время загрузки dlt) и записаны с запросами

### Task 2. Инцидент

**Expected result / Definition of Done:**
- Сбой подготовлен **заранее и описан в запечатанном виде** (что ломаешь и когда) — затем
  «забыт»: ты разбираешь его по симптомам, как дежурный
- По lineage найдено место возникновения (вверх от витрины) и все затронутые потребители (вниз);
  команды — в README
- Данные восстановлены перерасчётом; сверка и проверки зелёные

### Task 3. Постмортем

**Expected result / Definition of Done:**
- Запись в [`ops/incidents.md`](../../../../ops/incidents.md): что, когда заметили, влияние, причина
  (свойство системы, не триггер), MTTD и MTTR с расчётом, действия
- Хотя бы одно действие реализовано (новая проверка, алерт, контракт или идемпотентность), и
  повтор сбоя теперь ловится раньше (MTTD до и после)
