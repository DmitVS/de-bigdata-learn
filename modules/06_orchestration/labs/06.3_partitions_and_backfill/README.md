## Objective

Сделать загрузку продаж партиционированной по дням: загрузить всю историю backfill'ом,
перезагружать один день без дублей, запускать загрузку по появлению файла и по расписанию.
Это ответ на вопрос сети «как безопасно перезапустить прошлый период».

## Tasks

### Task 1. Партиции продаж

**Expected result / Definition of Done:**
- Ассет продаж bronze партиционирован по дням периода датасета; день берётся из ключа партиции,
  а не из «последнего файла»
- Повторная материализация одного дня не меняет число строк в bronze (запрос до и после в
  `queries.sql`)
- Партиционированные и непартиционированные ассеты (справочники, dbt) связаны так, как ты
  решил; решение и его следствия для «что пересчитать» — в README

### Task 2. Backfill всей истории

**Expected result / Definition of Done:**
- Backfill всех 97 дней прошёл; в bronze 4 850 000 строк дневных продаж (или своё число с
  объяснением grain)
- Записано время backfill и число запусков; политика backfill выбрана и обоснована
- Эксперимент: тот же период с другой политикой (диапазон партиций за запуск). Таблица «политика
  → запусков → время» в README. Что пришлось изменить в коде ассета?

**Steps:**
1. Что вернёт `context.partition_key`, если в запуске диапазон партиций? (урок 03, ловушки)
2. Как записать диапазон дней в Iceberg идемпотентно одной операцией?

### Task 3. Расписание и сенсор

**Expected result / Definition of Done:**
- Расписание ежедневной загрузки; проверка тиком на две даты (внутри периода и сегодня): какая
  партиция запрашивается — в README. Включено ли расписание и почему
- Сенсор на `s3://landing/freshretail/sales/`: новый файл → загрузка этого дня; повторная
  доставка → повторная загрузка; неизменённый файл → тик `SKIPPED`. Три сценария проверены
- В коде сенсора нет состояния, которое переживает тик в памяти процесса (урок 03, ловушка fsspec)

- Проверено; если были ошибки коммита или блокировки — текст ошибки и решение (пул, политика,
  ретрай) в README
