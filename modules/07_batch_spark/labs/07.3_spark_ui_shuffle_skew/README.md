## Objective

Научиться до запуска предсказывать, сколько будет стадий, где shuffle и какой алгоритм соединения
выберет Spark, а после — проверять это в UI и лечить медленные места. Данные — почасовые продажи
(108 млн строк train).

## Tasks

### Task 1. Предсказание → проверка: groupBy

**Expected result / Definition of Done:**
- Для трёх запросов к почасовым продажам (продажи по магазину и дню; медиана продаж по товару;
  число различных товаров с продажей по городу) записано **до запуска**: число стадий, есть ли
  частичная агрегация, примерный объём shuffle (больше или меньше 1 МБ)
- После запуска — фактические числа из UI или `StageReport`; расхождения объяснены

### Task 2. Предсказание → проверка: join

**Expected result / Definition of Done:**
- Два соединения почасовых продаж: со справочником магазинов и с дневными продажами того же
  магазина и товара (две большие стороны). Для каждого — предсказанный и фактический алгоритм
  (план до запуска и итоговый в UI → SQL), объём shuffle, время
- Что изменилось бы при `autoBroadcastJoinThreshold = -1` — проверено

### Task 3. Перекос

**Expected result / Definition of Done:**
- Найден запрос с перекосом на наших данных, отличный от примера урока (другой ключ или
  операция); доказательство — медиана и максимум времени задачи, распределение ключа
- Перекос устранён (broadcast, агрегация до соединения, соль — что подходит); время и метрики до
  и после в README; результат совпадает (сверка сумм)

### Task 4. AQE

**Expected result / Definition of Done:**
- Один из запросов выполнен с AQE и без: число задач после shuffle, время, итоговый план
- В README: что именно AQE поменял в твоих запросах
