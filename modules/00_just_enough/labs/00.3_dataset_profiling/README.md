## Objective

Прежде чем строить pipeline, нужно знать данные: гранулярность, ключ, объём, качество и
расхождения с документацией. Документация к данным ошибается чаще, чем кажется, — здесь
она уже расходится с фактом (865 vs 863 SKU, период до 2024-07-02 вместо 2024-06-07).

## Tasks

### Task 1. Схема

**Expected result / Definition of Done:**
- Таблица: колонка → тип → смысл (из карточки/статьи) → пример значения
- Ответ: какие колонки — массивы, какой длины, что означает индекс элемента

**Steps:**
1. Создай рядом с этим README файл `queries.sql`. Первой строкой запиши `CREATE VIEW sales AS …`
   из урока 09, шаг 2, — дальше все запросы обращаются к `sales`.
2. `make sql`, затем `.read modules/00_just_enough/labs/00.3_dataset_profiling/queries.sql`.
3. `DESCRIBE sales;` — имена и типы. `.mode line` + `SELECT * FROM sales LIMIT 1;` — пример
   значений.
4. Смысл колонок возьми из карточки датасета: `data/raw/freshretailnet_50k/README.md` или
   страница на Hugging Face.
5. Длину массивов проверь запросом (урок 09, шаг 6), смысл индекса — по карточке и статье.

### Task 2. Гранулярность и ключ

**Expected result / Definition of Done:**
- Сформулирован grain одной строки одним предложением
- Запрос, доказывающий уникальность предложенного ключа (0 дубликатов)
- Ответ: сколько строк **должно** быть при таком ключе, если бы каждая пара магазин×товар
  продавалась каждый день? Сколько есть на самом деле? Что это говорит о данных?

**Steps:**
1. Запиши гипотезу grain словами: «одна строка — это …».
2. Проверь её запросом уникальности (урок 09, шаг 5). Если есть дубликаты — посмотри их через
   `HAVING count(*) > 1` и уточни гипотезу.
3. Для «должно быть» посчитай точное число разных значений каждой колонки ключа
   (`count(DISTINCT …)`, не `SUMMARIZE`) и число дней периода (`dt::DATE`).
4. Сравни произведение с `count(*)` и запиши вывод.

### Task 3. Расхождения с документацией

**Expected result / Definition of Done:**
- По каждому расхождению (865 vs 863 SKU, период до 2024-07-02 vs 2024-06-07): гипотезы,
  запросы, которыми каждая проверена, и вывод. Допустимый вывод — «данные эту гипотезу
  опровергают» или «по одним данным расхождение не объясняется»: важно, чтобы он был доказан
  запросами
- Ответ: какие из этих фактов важны для pipeline (а какие — только для ML-бенчмарка)?

<details><summary>Подсказка</summary>

Файлов два. `read_parquet(..., filename = true)` добавит колонку с именем файла — сравни
сплиты между собой: периоды, магазины, товары. Для числа SKU проверь несколько гипотез: есть ли
товары только в одном файле, нет ли товаров, которые встречаются очень редко или без продаж, что
именно считает документация. Не каждое расхождение объясняется одной причиной.
</details>

**Steps:**
1. Выпиши из карточки датасета и статьи заявленные числа.
2. Посчитай те же величины по каждому файлу отдельно и по обоим вместе (урок 09, шаг 8).
3. Для каждого расхождения запиши гипотезы, проверь каждую запросом и сохрани запросы в
   `queries.sql`.
4. Перечитай в уроке 09 абзац про train / eval split и ответь на вопрос про pipeline.

### Task 5 (бонус). Первый взгляд на бизнес

**Expected result / Definition of Done:** 3 запроса и 3 наблюдения — задел для модуля 01:

- доля часов «нет на полке» по категориям первого уровня
- средние продажи в дни с промо и без

**Steps:**
1. Для часов разверни массив с номером элемента (урок 09, шаг 6) и сгруппируй по номеру.

   через `count(*) FILTER (…)` / `count(*)`.
3. Для промо выбери, какой флаг считать промо, и обоснуй выбор по карточке.
4. Под каждым запросом — одно наблюдение одним предложением.
