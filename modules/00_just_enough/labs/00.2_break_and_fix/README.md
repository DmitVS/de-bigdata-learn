# Лаба 00.2 · Сломать и починить

**Модуль:** [00 · Just enough](../../README.md) · **Дата начала:** YYYY-MM-DD · **Статус:** ⬜

## Objective

Инженер данных большую часть времени не пишет новый код, а выясняет, почему pipeline не
работает. Тренируем цикл **симптом → диагностика → причина → починка** на своём стеке, пока
цена ошибки — ноль. Каждый сценарий оформляем как мини-постмортем (формат из [`ops/incidents.md`](../../../../ops/incidents.md)).

## Key Terms

- **Симптом vs причина (root cause)** —
- **MTTD / MTTR** —
- **Restart policy** (`unless-stopped`, `no`) —
- **Идемпотентность** —

## Prerequisites

- Теория: [08 · Диагностика](../../theory/08_diagnostics.md)
- Лаба 00.1 выполнена, `make check` — все OK, `git status` чистый
- Инструменты диагностики: `make ps`, `make logs S=<сервис>`, `docker inspect`, `make check`

## Tasks

Для каждого сценария — запись в разделе «Результат»:

```
### Сценарий N
- Что сделал:
- Симптом (что увидел, дословно ошибка):
- Как диагностировал (команды):
- Причина:
- Как починил:
- Чему научился:
```

**Перед каждым сценарием:** предскажи письменно, что сломается. **После:** стек снова проходит `make check`.

### Сценарий 1. Сменили секрет S3

**Definition of Done:** запись по шаблону + ответ: почему после смены секрета часть проверок
проходит, а часть — нет? Какое состояние «помнит» старый секрет?

**Steps:** поменяй `S3_SECRET_KEY` в `.env` → `make restart` → `make check`. Найди причину и
почини **без** `make clean` (то есть не теряя данные).

<details><summary>Подсказка</summary>

Где ещё, кроме `.env`, записан секрет? Посмотри, что делает `lakekeeper/init.sh` и что он
делает, если warehouse уже существует. В Lakekeeper есть Management API для обновления
storage-credential у warehouse (UI: http://localhost:8181/ui).
</details>

### Сценарий 2. Занятый порт

**Definition of Done:** запись по шаблону + ответ: что именно не запустилось и как это видно?

**Steps:**
```bash
make down
docker run -d --rm --name port-thief -p 127.0.0.1:8888:8000 debd/workspace:local python -m http.server
make up
```
Разберись, почини (не убивая «вора» сразу — сначала найди его командой), затем `docker stop port-thief`.

### Сценарий 3. Упала база

**Definition of Done:** запись по шаблону + ответы: что происходит с `lakekeeper` при
недоступном Postgres? Какие проверки `make check` падают и почему именно они? Что сделает
Docker, если контейнер Postgres упадёт сам, а не будет остановлен тобой?

**Steps:** `docker stop debd-postgres-1` → `make check` → `make logs S=lakekeeper` → `docker start debd-postgres-1`.

### Сценарий 4. Ошибка в init-скрипте

**Definition of Done:** запись по шаблону + ответ: почему `make up` сообщает об ошибке, хотя
Postgres, Silo и Lakekeeper здоровы? Какой контейнер «виноват» и как найти его лог?

**Steps:** внеси опечатку в URL в `infra/docker/lakekeeper/init.sh` → `make restart` → найди и
исправь → `git diff` пустой.

### Сценарий 5 (бонус). Полный сброс

**Definition of Done:** запись + список: что потерялось, что сохранилось, что восстановилось само.

**Steps:** `make clean` → `make up` → `make check`. Где теперь бакет `scratch` из лабы 00.1?
Датасет в `data/raw`?
