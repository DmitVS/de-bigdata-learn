**Модуль:** [10 · Витрины и BI](../../README.md) · **Дата начала:** YYYY-MM-DD · **Статус:** ⬜

## Objective

Перенести витрины capstone из Iceberg в ClickHouse так, чтобы главные запросы дашборда читали
минимум данных, а перезалив не показывал пользователю пустую или половинную таблицу. Тренируем
выбор `ORDER BY`, замер стоимости запроса и предрасчёт итогов.

## Tasks

### Task 1. Ключ витрины под запросы дашборда

**Expected result / Definition of Done:**
- В README — три главных запроса будущего дашборда (из бизнес-вопросов лабы 01.2) с фильтрами
- Витрина продаж capstone загружена в ClickHouse в двух вариантах `ORDER BY`; DDL обоих — в
  `capstone/serving/clickhouse/`
- Таблица замеров: для каждого запроса и варианта — прочитано строк и байт, гранул по
  `EXPLAIN indexes = 1`, медиана времени из 10 запусков; размер таблиц на диске
- Выбран один вариант, выбор обоснован цифрами; вариант-проигравший удалён

**Steps:**
1. Подключи каталог Iceberg в ClickHouse (урок 03, шаг 1) и найди свои таблицы: `SHOW TABLES FROM lake`.
2. Запиши три запроса дашборда в README. Отметь, по каким колонкам каждый фильтрует.
3. Создай две таблицы MergeTree с разными `ORDER BY` и заполни их `INSERT … SELECT` из `lake`.
4. Сделай замеры с `SETTINGS log_comment` и собери их запросом к `system.query_log`.
5. Запиши вывод: какой ключ выбран и почему; сколько места заняли варианты.

### Task 2. Атомарный перезалив

**Expected result / Definition of Done:**
- Скрипт `capstone/serving/clickhouse/load_<витрина>.sql`: таблица-копия, загрузка, проверка,
  `EXCHANGE TABLES`, удаление копии
- Проверка в скрипте: число строк копии совпадает с Iceberg; если нет — скрипт падает до обмена
  (подсказка: `throwIf`)
- Доказано, что во время перезалива читатель не видит пустую таблицу: во втором терминале
  запрос `count()` в цикле, вывод — в README

**Steps:**
1. Напиши скрипт по схеме урока 03 (шаг 1, «Сборка целиком»).
2. Добавь проверку числа строк до обмена.
3. Запусти `make ch ARGS="--queries-file …"` дважды подряд. Второй запуск должен пройти без ошибок.
4. Во втором терминале во время загрузки выполняй `count()` к витрине каждые 0,2 с и сохрани вывод.

### Task 3. Предрасчёт итогов

**Expected result / Definition of Done:**
- Приёмник AggregatingMergeTree «город × день»: продажи, часы без товара, число строк,
  **число магазинов с продажами** (неаддитивная метрика)
- MV на таблицу продаж в ClickHouse и перенос истории без пересечения и без пропусков
- Запрос к приёмнику и прямой запрос к витрине дают одинаковые числа на 3 выбранных городах и днях
  (запросы и вывод — в README)
- Ответ в README: почему MV пустая сразу после создания; почему число магазинов нельзя хранить в
  SummingMergeTree; что сломается при перезаливе витрины через `EXCHANGE TABLES` (подсказка:
  к какой таблице привязана MV)

**Steps:**
1. Сначала запиши предсказание: сколько строк будет в приёмнике сразу после `CREATE MATERIALIZED VIEW`.
2. Создай приёмник и MV по образцу урока 03, шаг 3.
3. Перенеси историю и сверь итоги с прямым запросом.
4. Повтори перезалив из задачи 2 и проверь приёмник. Запиши, что увидел и как это исправить.
