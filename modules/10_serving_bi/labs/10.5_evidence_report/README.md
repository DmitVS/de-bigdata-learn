## Objective

Ответить на один бизнес-вопрос из лабы 01.2 страницей, где текст, SQL и графики живут вместе в
git и собираются в статический сайт. Тренируем отчёты как код: источник, запросы, компоненты,
сборку и ревью отчёта как кода.

## Tasks

### Task 1. Проект отчёта в capstone

**Expected result / Definition of Done:**
- Проект Evidence в `capstone/serving/report/` (структура — как в образце): источник через
  Trino на витрины capstone; `node_modules`, `.evidence`, `build` — вне git
- Сервис `evidence` показывает твой проект (подумай, что поменять в `serving.yaml` или как
  переопределить рабочую папку), страница открывается на http://localhost:3071

**Steps:**
1. Скопируй структуру образца; поменяй схему в `sources/…/connection.yaml`.
2. Опиши в `sources/…/*.sql` только нужные срезы витрин — не всю таблицу.

### Task 2. Страница-ответ

**Expected result / Definition of Done:**
- Страница по одному вопросу из лабы 01.2: вопрос, короткий вывод в начале, 2–3 графика,
  таблица, раздел «как считали» с определением метрики (из лабы 10.4)
- Числа в тексте не вписаны руками, а подставлены из запросов (`<Value>`)
- Есть хотя бы один фильтр (`<Dropdown>`), и графики на него реагируют

**Steps:**
1. Начни с вывода и вопроса, потом добавляй графики, которые его доказывают.
2. Проверь каждое число страницы против `mf query` или `make ch`.

### Task 3. Сборка и ревью

**Expected result / Definition of Done:**
- `npm run build` собирает сайт в `build/`; сайт открывается без сервера разработки
  (например, `npm run preview`)
- В README — сколько весит сборка и какие данные попали внутрь сайта (подсказка: папка с
  Parquet-файлами); почему важно, какие срезы ты выгружаешь в `sources`
- Изменение отчёта оформлено как коммит с понятным diff: ревьюер видит и текст, и SQL

**Steps:**
1. Запусти `npm run sources` и `npm run build` в контейнере `evidence`.
2. Найди в `build/` выгруженные данные и оцени их размер.
