# 05 · Состояние, чекпоинты, exactly-once и поток в Iceberg

> [!info] Урок одной фразой
> Сортировочный центр работает круглосуточно и держит в голове незакрытые ящики (состояние). Раз
> в 10 секунд он фотографирует всё сразу: ящики и закладки в каждом журнале (чекпоинт). После
> сбоя он восстанавливается с последней фотографии и перечитывает журналы с отмеченных мест — ни
> одно письмо не потеряно и не посчитано дважды. А готовые ящики он сдаёт на склад (Iceberg)
> только вместе с фотографией — поэтому на складе нет «полуготовых» поставок.

## Шаг 1. Состояние

**Проблема.** Оконный агрегат «средние осадки города за день» должен помнить сумму и количество
для каждого незакрытого окна, пока окно не закроется. Где это хранится и что будет при падении?

**Как устроено.** **Состояние** — данные, которые оператор Flink хранит между событиями: суммы
открытых окон, последние значения по ключу (changelog CDC), записи для соединений потоков.
Состояние разбито по ключу (`city_id`) и хранится в памяти taskmanager или на диске (RocksDB
для больших состояний).

**Что из этого следует.** Состояние растёт с числом ключей и временем: непрерывный агрегат по
`(город, день)` без окна копит строки за каждый день навсегда. Для таких запросов задают TTL
состояния (`table.exec.state.ttl`) — сколько хранить ключ без обновлений.

## Шаг 2. Чекпоинты

**Проблема.** Taskmanager упал. Состояние в его памяти пропало, а офсеты Kafka ушли вперёд. Как
восстановиться без потерь и без двойного счёта?

**Как устроено.** Каждые `execution.checkpointing.interval` (у нас 10 с) jobmanager запускает
**чекпоинт** (алгоритм асинхронных барьеров):

1. Источники вставляют в поток **барьер** с номером чекпоинта и запоминают свои офсеты Kafka.
2. Барьер идёт по графу вместе с событиями. Оператор, получив барьер со всех входов, сохраняет
   своё состояние и пропускает барьер дальше.
3. Когда барьер прошёл все операторы, чекпоинт завершён: есть согласованный снимок «офсеты
   источников + состояние всех операторов» в `state.checkpoints.dir` (у нас — том
   `flink-checkpoints`).
4. При сбое задание перезапускается с последнего завершённого чекпоинта: состояние
   восстанавливается, источники перематываются на сохранённые офсеты и перечитывают события.

**Что из этого следует.** Внутри Flink это даёт **exactly-once для состояния**: каждое событие
повлияло на восстановленное состояние ровно один раз. Но внешний мир мог уже получить результаты
между последним чекпоинтом и сбоем — их задание выдаст повторно. Чтобы и приёмник получил ровно
один раз, нужен приёмник, который участвует в чекпоинте (шаг 3).

## Шаг 3. Exactly-once до приёмника: Iceberg

**Проблема.** Окно закрылось, строка записана в Iceberg, через секунду — сбой, восстановление с
чекпоинта до этой записи. Строка запишется второй раз?

**Как устроено.** Приёмник Iceberg во Flink работает по схеме **двухфазного коммита**:

- между чекпоинтами writer пишет Parquet-файлы в S3, но **не коммитит** их в таблицу — читатели
  их не видят;
- на чекпоинте список файлов сохраняется в состоянии; после **успешного** завершения чекпоинта
  коммиттер делает один коммит Iceberg (снапшот) со всеми файлами этого чекпоинта;
- при сбое до коммита файлы так и не попадают в таблицу. Задание повторяет события с офсетов
  чекпоинта и пишет их заново, и в таблице они окажутся один раз.

**Что из этого следует.** Сквозная гарантия exactly-once = источник с перематываемыми офсетами
(Kafka) + состояние в чекпоинтах + приёмник с транзакционным коммитом (Iceberg, Kafka с
транзакциями). Цена — **задержка**: данные видны в Iceberg только после чекпоинта (у нас до 10 с).

> [!example]- Попробуй сам: поток в Iceberg и коммиты на чекпоинтах
> ```bash
> make flink-sql ARGS="-f /workspace/modules/08_streaming_cdc/demo/flink/02_weather_to_iceberg.sql" 2>&1 | grep -E "Job ID|ERROR"
> ```
> Подожди 40 с и посмотри таблицу, затем отправь ещё два дня показаний и снова подожди 30 с:
> ```bash
> make shell
> cd modules/08_streaming_cdc/demo
> cat > /tmp/check.py <<'EOF'
> import os
> from pyiceberg.catalog import load_catalog
> t = load_catalog("lh", type="rest", uri=os.environ["ICEBERG_CATALOG_URI"],
>                  warehouse=os.environ["ICEBERG_WAREHOUSE"]).load_table("sandbox_flink.city_weather_daily")
> rows = t.scan().to_arrow()
> days = sorted({str(d)[:10] for d in rows.column("window_start").to_pylist()})
> print("строк:", rows.num_rows, "снапшотов:", len(t.history()), "дни:", days)
> EOF
> python /tmp/check.py
> python -m streaming_demo.weather_producer --from 2024-04-04 --to 2024-04-05
> sleep 30 && python /tmp/check.py
> exit
> ```
> UI Flink <http://localhost:8086> → Running Jobs → задание → Checkpoints.
> **Увидишь:** `Job ID …` в клиенте; затем `строк: 36 снапшотов: 1 дни: ['2024-04-01',
> '2024-04-02']`, после второй порции — `строк: 72 снапшотов: 2` и дни по 2024-04-04; в UI —
> завершённые чекпоинты каждые ~10 с без ошибок.
> **Почему:** закрытые окна попадают в таблицу коммитом на ближайшем чекпоинте; чекпоинт без новых
> файлов снапшот не создаёт. Последний день каждой порции ещё открыт: watermark не перешёл его
> конец, пока не придут события следующего дня.

## Шаг 4. Мелкие файлы и как с ними жить

**Проблема.** Коммит каждые 10 секунд — это минимум один файл на партицию каждые 10 секунд: 8 640
файлов в сутки. Чтение такой таблицы медленное (модуль 03, модуль 07).

**Как устроено.** Варианты, которые комбинируют:

- **реже чекпоинты** для приёмника в Iceberg (минута, пять) — меньше файлов, больше задержка;
- **компактизация** по расписанию — `rewrite_data_files` из Spark (модуль 07, урок 04) или
  встроенная в задание Flink поддержка (`write.upsert…`, отдельные задания обслуживания);
- **агрегировать до записи** — писать окна, а не сырые события.

**Что из этого следует.** Потоковая запись в lakehouse — это всегда два процесса: запись
(частая, мелкая) и обслуживание (редкое, тяжёлое). Без второго таблица деградирует.

> [!warning] Ловушка: остановленное задание держит открытые окна
> Для плановой остановки используй **stop with savepoint**: снимок, с которого задание продолжит.
> Если остановить задание `INSERT INTO` через Cancel, незакрытые окна и незакоммиченные файлы
> пропадут. Их пересчитают только после перезапуска с чекпоинта или с офсетов группы.

**Остановка и очистка.** Задание из шага 3 работает, пока его не остановить:

```bash
docker exec debd-flink-jobmanager-1 ./bin/flink list -r            # ID работающих заданий
docker exec debd-flink-jobmanager-1 ./bin/flink cancel <JOB_ID>
make shell
python - <<'EOF'
import os
from pyiceberg.catalog import load_catalog
c = load_catalog("lh", type="rest", uri=os.environ["ICEBERG_CATALOG_URI"], warehouse=os.environ["ICEBERG_WAREHOUSE"])
for t in c.list_tables("sandbox_flink"):
    c.purge_table(t)
c.drop_namespace("sandbox_flink")
EOF
exit
```

## Шпаргалка

| Хочу | Как |
|---|---|
| Интервал чекпоинтов | `execution.checkpointing.interval` (у нас 10 с, `streaming.yaml`) |
| Где чекпоинты | `state.checkpoints.dir` → том `flink-checkpoints` |
| Каталог Iceberg во Flink | `CREATE CATALOG lh WITH ('type'='iceberg','catalog-type'='rest', …, 'header.X-Iceberg-Access-Delegation'='vended-credentials', 'io-impl'='org.apache.iceberg.aws.s3.S3FileIO')` |
| Задания | `./bin/flink list -r`, `./bin/flink cancel <id>`, `./bin/flink stop --savepointPath … <id>` |
| TTL состояния | `SET 'table.exec.state.ttl' = '1 d'` |
| Мелкие файлы | реже чекпоинты, компактизация (модуль 07) |

## Типичные ошибки

| Симптом | Причина | Как проверить | Как чинить |
|---|---|---|---|
| Таблица Iceberg пустая, задание работает | окна не закрылись (watermark) или нет чекпоинтов | UI: Watermarks, Checkpoints | данные следующего периода; интервал чекпоинтов |
| `Checkpoint expired` / не завершается | нет общего хранилища, большое состояние | UI → Checkpoints | общий том / S3, TTL состояния |
| Состояние растёт бесконечно | непрерывный агрегат без TTL | UI → размер чекпоинта | `table.exec.state.ttl` |
| Тысячи файлов в таблице | частые коммиты | `t.files` | реже чекпоинты, компактизация |
| `NoClassDefFoundError: org/apache/hadoop/conf/Configuration` | нет Hadoop client для Iceberg во Flink | лог задания | `hadoop-client-api/runtime` в `lib` (сделано в образе) |

## Проверь себя

Карточки — в [flashcards.md](../flashcards.md).

> [!question] 1. Почему чекпоинт сохраняет офсеты Kafka вместе с состоянием, а не отдельно?
> > [!success]- Ответ
> > Только согласованная пара «офсеты + состояние» позволяет восстановиться без потерь и двойного
> > счёта: состояние ровно такое, каким его сделали события до сохранённых офсетов.

> [!question] 2. Как Iceberg-приёмник избегает дублей после сбоя?
> > [!success]- Ответ
> > Файлы коммитятся в таблицу только после успешного чекпоинта. Файлы, записанные после последнего
> > чекпоинта, не попадают в таблицу; события перечитываются с офсетов чекпоинта и пишутся заново.

> [!question] 3. Ты уменьшил интервал чекпоинтов до 1 с. Что выиграл и что проиграл?
> > [!success]- Ответ
> > Данные видны в Iceberg быстрее, а при сбое меньше перечитывать. Но файлов и снапшотов в 10 раз
> > больше, а накладные расходы на чекпоинты выше.

> [!question] 4. «Exactly-once» у Flink с приёмником, который пишет в Postgres простым INSERT. Будут ли дубли?
> > [!success]- Ответ
> > Возможны: состояние восстановится ровно один раз, но INSERT между чекпоинтом и сбоем
> > повторится. Нужен транзакционный приёмник или идемпотентная запись (upsert по ключу).
